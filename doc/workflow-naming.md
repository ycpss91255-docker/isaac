# Workflow naming

How GitHub Actions workflows and jobs in this repo are named (isaac#443).
`script/ci/lint_workflow_names.py` checks every rule below; it runs in the
`docs-unit` job and in `test/unit/pytest/test_workflow_naming.py`.

## Why

The names used to be chosen one by one: some files named after a function,
some after a source; display names with and without a parenthesised note;
job ids with and without a `call-` prefix. A name should say what kind of
workflow it is and, for CI, which scope it belongs to, because branch
protection, badges and docs refer to those names.

## Categories

| Category | Meaning | Examples |
|---|---|---|
| `ci` | Checks a change. Runs per scope group (core, gui, stream, headless, docs; isaac#434). | `ci-stream-smoke.yaml` |
| `release` | Cuts or publishes a release. | `release-...yaml` (today the release job lives in `main.yaml`) |
| `bot` | Tracks something upstream and opens an issue or PR (base version, official Isaac Sim, dependabot). Runs no tests. | `bot-isaac-sim-version.yaml` |
| `tool` | A utility started by hand. | `tool-...yaml` |

This follows the org's existing habit: base names its files by function
(`build-worker.yaml`, `release-worker.yaml`, `tool-version-watch.yaml`).

## Rules

1. **File name**: `<category>-<feature>.yaml`. Lowercase kebab-case, extension
   `.yaml` (not `.yml`). A CI workflow for one scope puts the group first:
   `ci-<group>-<what>.yaml`, e.g. `ci-stream-smoke.yaml`. CI path rules rely on
   that: a change to `ci-stream-*` selects the stream group.
2. **Display name** (`name:`): `<Category>: <Feature Words>`, the feature words
   of the file name in Title Case. `ci-stream-smoke.yaml` is `CI: Stream Smoke`.
   Categories are written `CI`, `Release`, `Bot`, `Tool`. No parenthesised
   notes.
3. **Job id**: lowercase kebab-case. No `call-` prefix (the id says what the job
   is, not how it is run) and no job-level `name:`: the check name is then the
   job id, which is what branch protection and `needs:` refer to.
4. **CI job ids** (`main.yaml` and `ci-*.yaml`): either `changes`, `gate` or
   `release`, or start with a scope group: `core-`, `gui-`, `stream-`,
   `headless-`, `docs-`. Examples: `core-unit`, `core-gpu`, `core-build`,
   `stream-smoke`, `docs-unit`.
5. **Required check**: only `gate`. It summarizes every other job and passes
   when each one succeeded or was skipped, so renaming a job never touches
   branch protection (see ADR-0011, 2026-11-21 update).

## Exemptions

Exempt by exact file name from rules 1 and 2 (their jobs still follow rules 3
and 4); each file is owned by base's `init.sh`:

| File | Why it keeps its name |
|---|---|
| `main.yaml` | The org-wide entry workflow: every ycpss91255-docker repo has a `main.yaml`, and base's `init.sh` creates it. It carries both CI and release, so it has no single category. Display name stays `Main CI/CD`. |
| `base-version-monitor.yaml` | Generated by base's `init.sh` (`_sync_base_monitor_workflow`), which creates exactly this path when it is absent. Checked before touching it: `init.sh` only creates, it never overwrites an existing file, so edits to the content would survive an upgrade, but a renamed file is regenerated beside the renamed one on the next base upgrade. It keeps its original name and content (display name `Base Version Monitor`, job `check`), which also keeps it identical to every other base-based repo. Its weekly `schedule` is the one allowed schedule: a bot that tracks a release, not a test run. |
| `publish-stream-source.yaml` | Removed in isaac#432 (the producer image moves out). Not renamed first; exempt from every rule until then. |

## Renames done with this rule

| Before | After |
|---|---|
| `stream-smoke.yaml`, name `Stream Smoke (GPU)` | `ci-stream-smoke.yaml`, name `CI: Stream Smoke` |
| job `call-docker-build` | `core-build` |
| job `call-release` | `release` |
| job `hosted-unit` | `core-unit` / `stream-unit` / `docs-unit` |
| job `gpu-integration` | `core-gpu` |

The required checks changed once, with isaac#434, from
`call-docker-build / docker-build` and `gpu-integration / gpu` to `gate`.

## Adding a workflow

Pick the category, name the file `<category>-<feature>.yaml`, set `name:` to
`<Category>: <Feature Words>`, give CI jobs a group prefix, and run
`python3 script/ci/lint_workflow_names.py`. A bot or tool workflow that has to
be generated by base keeps the generated name and goes on the exemption list
with the reason.
